The three things we would not compromise

1 · Provenance is a data model, not a UI label

2 · The review queue is the only write path to a fact

Every ingestion path is covered by a test that runs the same import twice and asserts zero new writes. Emails are keyed on Internet Message‑ID, documents on SHA‑256, deals on a normalised name key.

06

Our approach to AI‑assisted reading

MEASURED · STAGED · NEVER AUTO‑PUBLISHED

Your brief already states the right principle: nothing read automatically counts as fact. Our job is to make that principle measurable rather than merely asserted — so that a reviewer trusts the queue, and so that trust is earned with numbers rather than claims.

How we keep a person in the loop

  • The queue is the only write path. There is no code path by which an extracted value becomes Validated without a logged human decision. This is enforced in the service layer and covered by a test, not left to UI discipline.
  • Locator‑first extraction. Every claim carries document SHA‑256, page/paragraph/cell locator, the exact source span, period, currency, capture method, and model + prompt version. A reviewer can jump to the span in the original.
  • Provenance is separate from approval. Source, period, currency, date and capture method are stored apart from who approved it and when — exactly as your brief requires.
  • Acceptance requires opening the evidence. We log that the reviewer viewed the source excerpt before accepting. This is a nudge, not a barrier, but it makes rubber‑stamping visible in the metrics.
  • Corrections create revisions. The original value, the corrected value, the reviewer, the reason and the timestamp are all retained and diffable. Nothing is overwritten.
  • Confidence is shown, never acted on. A high‑confidence claim is still a claim. Confidence only affects queue ordering, never publication.
  • Disagreement is escalated, not averaged. A second extraction pass that disagrees on value or unit flags the claim as Conflicting automatically, and both readings are kept.

How we test accuracy

  • Golden set. 150–250 labelled claims drawn from real, anonymised documents across the 17 companies, refreshed quarterly and versioned in the repository.
  • Precision gate. A field type may only auto‑stage as "high confidence" once field‑level precision is ≥ 0.95 on the golden set. Below that it stages as normal confidence and sorts lower.
  • Recall reported, never used to bypass review. We publish recall so you know what extraction is missing, but a low recall never causes a value to be inferred.
  • Unit normalisation tested separately. Currency, percentage, and per‑month versus per‑year errors are where financial extraction actually fails, so they have their own test suite and their own metric.
  • Shadow mode for every change. A new prompt or model version runs in parallel over the last 30 days of documents; a human reviews the diff report before promotion. No silent swaps.
  • Drift monitoring. Weekly acceptance rate and correction rate by document type and by company; an alert fires when the correction rate exceeds 20%.
  • Cost per call recorded from M2 onwards — not deferred to M6 — so the assistant's budget is known before it ships, and administrators can see usage and spend.
  • Failure is visible. A failed read is retried, then shown as failed with the reason. Nothing is silently dropped.

The metric we would put on your dashboard from day one

Reviewer correction rate — the share of staged claims a human changes before accepting. It is the single number that tells you whether the AI reading is trustworthy, and it is the number that tells us where to improve extraction. We propose a target of below 15% by the end of the warranty period, measured per document type, with the baseline established in week 5 against your real sample data. We would rather show you an honest baseline in week 5 than a flattering one in week 26.

Training and confidentiality

No firm, portfolio or deal data is used for model training. We configure the Anthropic relationship accordingly, retain prompts and responses only as long as needed for audit and cost accounting, minimise the context sent with each call, and record the model and prompt version against every claim so an answer can be reproduced. Data of private companies is treated as confidential and accessed only after NDA.

What we would change about the brief

  • Split M4 into two acceptances. Pipe mechanics and record first; board, table, filters and configuration second. It shortens the longest unbroken stretch of risk from eleven weeks to about six.
  • Freeze the custom‑field type list now, in writing, at the eight types named. Adding a type later touches six surfaces and should be priced as such.
  • Add a reviewer SLA and queue‑ageing report from day one. The greatest threat to a human‑in‑the‑loop system is not bad extraction; it is a queue nobody empties. Ageing by claim and by company makes that visible.

  • Build an evidence viewer with locator highlighting in M2. It is the single largest reviewer‑speed win available and it is cheap while the extraction layer is being written; retrofitting it later is not.

  • Treat dark mode and resizable modules as M7 candidates if schedule pressure appears. They are real requirements but they are polish; provenance and the queue are the product.
